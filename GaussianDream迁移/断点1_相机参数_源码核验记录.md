## RoboTwin 精确源码证据

### 内参配置

`task_config/_camera_config.yml:11-19`：

```text
D435:       fovy=37°, w=320, h=240
Large_D435: fovy=37°, w=640, h=480
L515:       fovy=45°, w=320, h=180
Large_L515: fovy=45°, w=640, h=360
```

`camera.py:55-56` 显示默认 `head_camera_type` 和 `wrist_camera_type` 都是 `D435`。因此默认 RoboTwin 相机图像是 320×240，FOV 是 37°。SAPIEN 实际 K 可由 `camera.get_intrinsic_matrix()` 读取，见 `camera.py:299-305`。

### 静态相机的外参构造

`camera.py:92-120` 和 `camera.py:174-202` 使用：

```text
cam_pos = camera_info["position"]
cam_forward = camera_info["forward"]
cam_left = camera_info["left"]
up = cross(cam_forward, cam_left)
mat44[:3,:3] = [cam_forward, cam_left, up]
mat44[:3,3] = cam_pos
camera.entity.set_pose(sapien.Pose(mat44))
```

这说明 embodiment 的静态相机 pose 是 camera-to-world 风格的 pose。Gaussian Rasterizer 要使用 world-to-camera `viewmatrix`，因此必须在导出配置时明确求逆和坐标轴约定，不能直接把 `mat44` 当 `viewmatrix`。

### wrist 相机不是静态外参

`camera.py:134-148` 创建左右腕相机；`camera.py:286-293` 每次根据左右机械臂 pose 更新：

```python
self.left_camera.entity.set_pose(left_pose)
self.right_camera.entity.set_pose(right_pose)
```

因此：

- wrist 相机的 K 可以静态保存；
- wrist 相机的 T_cam 不能只保存一套静态常量；
- 如果 Gaussian Renderer 使用 wrist RGB，必须提供逐帧 wrist pose，或者第一版只用固定 head/top view；
- 原先“三个 view 都用静态 T_cam”的规格需要修正。

### 相机随机化

`camera.py:45` 保存 `random_head_camera_dis`；`camera.py:92-101` 会向 head/static camera position 加随机偏移。如果训练数据生成时启用了该参数，head 外参也不是单一静态常量。

## 对断点 1 的修正结论

第一版建议：

```text
head/top view：确认 random_head_camera_dis=0 后，使用固定外参
wrist views：可继续作为 3D encoder 的 RGB 输入，但暂不用于需要世界坐标投影的 Gaussian render loss
```

如果必须渲染 wrist view，需要扩展数据接口保存每帧相机 pose，不能继续使用静态 `robotwin_camera.json` 的 T。

静态 camera JSON 仍可以保存已核验的 D435/L515 内参；head 的具体 position/forward/left 依赖 RoboTwin embodiment 资产，主仓库 tree 中没有该资产，需要先运行 RoboTwin 的资产下载流程。

## hy4 提出的 HDF5 路径核验

该判断有源码依据，但适用范围是 RoboTwin 原始 pkl/HDF5 数据链路：

1. `envs/_base_task.py:447` 在每个 observation 中先写入 `self.cameras.get_config()`；
2. `envs/camera/camera.py:295-305` 的 `get_config()` 为每个相机写入：
   - `intrinsic_cv`
   - `extrinsic_cv`
   - `cam2world_gl`
3. `envs/utils/pkl2hdf5.py:57-68` 会递归保存这些 numpy 数组，因此原始 HDF5 理论上保留逐帧相机配置。

但是 LingBot 当前的 RoboTwin → LeRobot 转换脚本：

```text
LingBot/experiment/robotwin/README.md
RoboTwin/policy/GO1/scripts/convert_aloha_data_to_lerobot_robotwin.py
```

在 `load_raw_episode_data()` 中只读取：

```text
observations/qpos
observations/images/cam_high
observations/images/cam_left_wrist
observations/images/cam_right_wrist
action
```

`populate_dataset()` 也只把图像、state、action、velocity、effort 写入 LeRobot，没有复制 `intrinsic_cv / extrinsic_cv / cam2world_gl`。

### 最终结论

- 如果直接使用 RoboTwin 原始 HDF5：不需要下载 embodiment 资产，可以从每帧 observation 读取 K/T；
- 如果继续使用 LingBot 当前 LeRobot 数据集：相机 metadata 已被转换脚本丢弃，不能直接读取；
- 因此最优方案是修改转换链路，把 camera metadata 保存为 sidecar 或 LeRobot episode metadata，再由 LingBot dataset 返回；
- 直接下载 embodiment 仍可用于生成/验证相机配置，但不是读取已生成 HDF5 相机参数的必要条件。

当前 `robotwin_camera.json` 暂不填入静态 wrist T；后续代码应优先支持逐帧 metadata，静态 JSON 只作为没有 metadata 时的固定 head-camera fallback。

## 已落地的无 embodiment 方案

已在 LingBot 分支加入：

```text
experiment/robotwin/extract_camera_metadata.py
lingbotvla/models/vla/geometry/camera_metadata.py
```

运行提取脚本会从原始 RoboTwin HDF5 的 `observation/*_camera` 节点读取三类矩阵，生成每个 episode 的 `*.camera.npz` 和按输入排序的 `manifest.json`。训练数据加载器在配置 `data.camera_metadata_root` 后，会按 `episode_index + frame_index` 把以下张量带入 batch：

```text
camera_intrinsics   [3, 3, 3]
camera_extrinsics   [3, 4, 4]  # world_to_camera
camera_cam2world    [3, 4, 4]
camera_valid_mask   [3]
```

因此当前断点一不再依赖下载 embodiment。需要注意的是，这条链路的输入必须是包含 `observation` 相机元数据的原始 HDF5；已经转换成 LeRobot、且转换时未生成 sidecar 的旧数据无法事后恢复这些矩阵。

多数据集训练时，每个 LeRobot 数据集应使用自己的 sidecar `manifest.json`，放在 `camera_metadata_root/<数据集目录名>/` 下；加载器按各自数据集的局部 `episode_index` 读取，避免不同任务的 episode 编号互相错位。
